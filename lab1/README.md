# Лабораторная работа 1 Вариант 3

Консольный верификатор доказательств в исчислении высказываний.
Базовые связки: отрицание и дизъюнкция. Правила: MP и атомарная подстановка β.

## Быстрый запуск

Нужен Python **3.10 или новее**. Устанавливать пакеты через pip не требуется.
В PowerShell откройте папку проекта и выполните:

```powershell
py -3 lab1.py
```

Если команды `py` нет, используйте `python lab1.py`. Можно также открыть
`start.cmd` двойным щелчком. Для завершения введите `:quit`.

Готовая демонстрация из семи корректных строк:

```powershell
py -3 lab1.py --demo
py -3 lab1.py --file examples/demo.txt
```

Тесты и полная проверка с сохранением протоколов:

```powershell
py -3 -m unittest discover -s tests -v
py -3 tools/verify.py
```

В Linux/macOS те же команды запускаются с `python3` вместо `py -3`.
Другой физический компьютер и эти ОС в рамках работы не проверялись.

## Ввод формул

| Конструкция | Допустимая запись |
|---|---|
| Переменная | Одна латинская буква `a`–`z` или `A`–`Z` |
| Математическая буква из PDF | `𝑝` нормализуется в `p` |
| Отрицание | `¬p`, `~p`, `!p` |
| Дизъюнкция | `p ∨ q`, `p | q` |
| Импликация как сокращение | `p ⊃ q`, `p → q`, `p -> q` |
| Скобки | `((p))`, `(p | q) -> r` |

Импликация `A -> B` раскрывается в `~A | B` до проверки. Результат
печатается в базисе ¬,∨, чтобы пользователь видел настоящее дерево.
Опция `--ascii` заменяет в печати формул ¬ и ∨ на `~` и `|`.

Приоритет: **¬, затем ∨, затем ⊃**. Бинарные операции группируются слева.
Согласно лекции 1, слайд 16, `a -> b -> c` означает `(a -> b) -> c`.
Для правой группировки пишите `a -> (b -> c)`.

Переменные однобуквенные: `mn`, `p1`, `p_q`, `p'` недопустимы.
В варианте 3 буквы `f` и `t` являются переменными, специальных констант нет.
Связки ∧, эквивалентность, знак равенства, кванторы и λ-термы не поддерживаются.

## Команды сеанса

| Команда | Действие |
|---|---|
| `:help` | Справка |
| `:axioms` | Семь исходных аксиом и их деревья в базисной записи |
| `:list` | Все успешно принятые строки и названия обоснований |
| `:tree p -> q` | Показать дерево, не добавляя формулу в доказательство |
| `:reset` | Очистить доказательство и начать новый сеанс с аксиомами |
| `:quit` | Завершить программу |

В пакетном файле одна формула занимает одну строку. Пустые строки и строки,
начинающиеся с `#`, игнорируются. Команды `:...` предназначены для
интерактивного режима. Файл должен быть в UTF-8, в том числе допускается BOM.

Коды выхода пакетного режима: `0` — все формулы приняты; `1` — есть
отклоненные строки; `2` — ошибка аргументов или чтения файла. Обработка
продолжается после отклоненной строки, но эта строка не попадает в базу.
Пример ожидаемого отказа: `py -3 lab1.py --file examples/negative.txt`.

## Семь аксиом варианта 3

1. `p -> (p | q)`.
2. `(p | p) -> p`.
3. `(p | (q | r)) -> (q | (p | r))`.
4. `(q -> s) -> ((p | q) -> (p | s))`.
5. `~~p -> p`.
6. `(~q -> ~p) -> (p -> q)`.
7. `~p | p`.

Аксиомы трактуются как схемы, согласно уточнению преподавателя.
Например, `a -> (a | b)` принимается сразу как экземпляр A1 с
подстановками `p := a; q := b`. Несколько параметров схемы могут
заменяться одновременно, но все вхождения каждого параметра обязаны
соответствовать одному и тому же дереву.

`(~~~q -> ~q) -> (q -> ~~q)` принимается непосредственно как экземпляр
**A6** с подстановками `p := q; q := ~~q`. Формула не упрощается и
не преобразуется перед сопоставлением. Если нужны MP или β, программа
пишет соответствующее правило; одной семантической эквивалентности
недостаточно, чтобы назвать выражение экземпляром аксиомы.

Пункт 7 задания содержит также равенство с `¬p ⊃ p ⊃ p`.
В программе A7 — формула слева `¬p ∨ p`. Знак `=` не является связкой.
Правая запись не добавляется как отдельная аксиома. Точное толкование
этой неоднозначной записи и другие неточности исходников объяснены
в [разборе материалов](docs/MATERIALS_REVIEW.md).

## Что проверяет программа

Сначала парсер строит неизменяемое абстрактное синтаксическое дерево.
Затем проверяется одно из оснований:

1. Прямое структурное совпадение со схемой аксиомы; выводятся ее номер
   и все согласованные подстановки. Это проверяется раньше MP и β.
2. Повтор уже доказанной формулы со ссылкой на ее первое основание.
3. MP: доступны и `A -> B`, и **точно та же** формула `A`.
4. β: из одной доступной формулы все вхождения **одной** переменной
   одновременно заменяются одним и тем же деревом `X`.

Одна подстановка может вставлять сложную формулу и содержать исходную
переменную внутри вставляемого выражения. Вставленное дерево повторно
не заменяется. Частичная замена или замена двух разных переменных
за один шаг **β** отвергаются. Это ограничение не относится к распознаванию
экземпляров схем аксиом. Успешное обоснование содержит ссылки на аксиомы
или более ранние строки, а для β — переменную и найденную подстановку.

Программа не ищет доказательство автоматически и не объявляет каждую
тавтологию допустимым очередным шагом. «Шаг не обоснован» не означает
«теорема недоказуема». Коммутативность, ассоциативность, удаление двойного
отрицания, α-переименование и теорема дедукции автоматически не применяются.

Ограничения на одну формулу: 4096 символов, 511 узлов раскрытого дерева,
глубина 80; один сеанс — 1000 принятых строк. При превышении выводится
диагностика. `:reset` начинает новый сеанс.

## Файлы результата

- `lab1.py`, `proofchecker/` — программа.
- `tests/` — автоматические проверки на стандартном `unittest`.
- `examples/` — положительный и отрицательный ввод.
- `docs/MATERIALS_REVIEW.md` — разбор всех лекций, семинаров и страниц задания.
- `docs/MATERIALS_MANIFEST.json` — состав и SHA-256 всех 26 исходных файлов.
- `docs/DEFENSE.md` — сценарий демонстрации и ответы для защиты.
- `docs/REQUIREMENTS.md` — соответствие реализации требованиям задания.
- `evidence/` — фактические протоколы программы и тестов.
- `output/LR1_variant3.docx`, `output/LR1_variant3.pdf` — отчет.
- `output/LR1_variant3.zip` — комплект исходников, документов и протоколов.

Исходные учебные материалы не изменены. В итоговом ZIP они не дублируются;
их перечень и контрольные суммы сохранены. Локальные пути интерпретаторов
в протоколе отражают среду проверки, но не используются программой.

Для повторного построения DOCX служит `tools/build_report.py` и библиотека
`python-docx` (только инструмент подготовки отчета, не зависимость программы).
Экспорт PDF выполнен установленным Microsoft Word и проверен визуально.
